# Android feature follow-up — 2026-09-30

Scope: read-only review of OpenSCQ30 `master` at `bc77a29` (per-model Rust sources), its **unmerged** A3953 [PR #384](https://github.com/Oppzippy/OpenSCQ30/pull/384), [official P40i Safe Volume help](https://service.soundcore.com/article-description/How-to-Increase-Volume-on-soundcore-P40i-When-Connected-to-an-iPhone), and SoundControl's independent renderer/helper transport gates. The upstream author's real-device observations are credited to that author, **not** physical verification by SoundControl. A reference `send_with_response` waits for a packet with the same command (retries 500/1000/1500 ms); it **does not validate ACK body/status or perform a post-write state requery** (`common/packet/packet_io_controller.rs`). A simulated ACK is not proof of device persistence. SoundControl will not permit a new write without an exact-SKU validation/confirmation transaction and independent helper gate.

`01:01` means a device state request, `09 FF 01:01` the state reply; default Soundcore framing is `08 EE 00 00 00 CAT TYPE lengthLE payload additive-checksum`. **A3116 is an exception: OpenSCQ30 configures `ChecksumKind::None` and its own DSP service UUID, so generic SoundControl frame builders/helper MUST NOT be reused for this speaker.** `LEN` below means complete framed length (=10+payload) only for default-checksum profiles.

## Model-specific desktop feature evidence matrix

The **Status** column uses only the requested vocabulary. `VERIFIED READ`
means a strict, exact-SKU read-only UI exists; it does **not** certify a setter.
`VERIFIED WRITE` requires a validated response, fresh reread and reconnect
confirmation; **none of the newly investigated writes qualifies**. `PARTIAL`
means a readable field or reference operation exists but lacks the desktop
lifecycle. `REFERENCE ONLY` describes upstream packet builders without a safe
local implementation. `UNKNOWN` means no evidenced device command here;
`UNSUPPORTED` rejects cross-model assumptions. Physical-device validation
is documented separately in `HARDWARE-VALIDATION.md`.
`01:01` is the existing request; `09 FF 01:01` is its checksummed reply.
No write command in this matrix was added to either TX allowlist.

## Gesture encodings and limits

**04:81 source index (not a supported SoundControl command):** the common
per-ear action writer is registered by A3330 (media only), A3388, A3876,
A3909, A3926, A3930, A3931, A3933, A3936, A3944, A3945, A3947,
A3948, A3949, A3951, A3952, A3954, A3955, A3957, A3959, A3968,
D1101, D1202 and D1301; A3035/A3040/A3062 have their own single
headphone-button form. The model row above is a **source index**, not a claim
that each action ID, side, press type, enabled flag or full readback is
interchangeable. A3330 uses `04:87` specifically for its **call** configuration,
not for every button. A3954 also models up/down slide gestures. A3945 supports
bulk `04:84`. The A3953 open PR is excluded from verified coverage. A3945 Life Note 3S additionally has a fully pinned 72-byte read-only state: TWS status bytes 0–1, pairs 54–65 (strict flag plus action, connected low nibble on first four, single-byte action on last two), strict BassUp byte 70, gaming byte 68, case byte 69 and color 71. No firmware floor or ACK/reconnect persistence for its writes was found.

OpenSCQ30 `common/structures/button_configuration.rs` and each model's `BUTTON_CONFIGURATION_SETTINGS` define `LeftSingle/Double/Triple/Long/SlideUp/SlideDown` and right counterparts, but their **available actions and button IDs are per model**. `ButtonSide`: 0 left, 1 right. `ActionKind::Single` is one byte; `TwsLowBits` stores action for connected TWS status in the low nibble, disconnected in the high nibble; disabled often 0xF. Enabled flag can be absent, a strict 0/1 byte or two status nibbles. The reference preserves the other nibble when changing only one status. It sends `04:83` separately when enabled changes and `04:84` bulk when the model supports it and multiple buttons differ; A3945 is such a model. A3035/A3040/A3062 expose a **single** double-press action in their headphone-specific button modules, not a per-ear 1/2/3/hold matrix. No public generic `04:01` standalone configuration query was found: button assignments are part of `01:01` full state. Upstream `send_with_response` validates only the reply command key, not success status; no robust write→fresh requery→reconnect proof was found for these SKUs. A3953 PR author reports a physical button check on *their* Liberty 4, but the PR is unmerged and SoundControl lacks an A3953 state profile.

## Lifecycle decisions

**Now implemented, read-only:** the existing `01:01` handshake is the query. `parseObservedFeatures` accepts only checksum- and length-valid `09 FF 01:01` on a verified exact-SKU profile and requires at least the reference full-state sample length (A3040 142, A3954 165, D1202 152) and **exact** source-parse-complete lengths for A3945 72 and D1301 150. A short or overlong A3945/D1301 body cannot confirm the model layout or refresh its case/observations. Each enum, 0/1 flag and 75–100 dB step is validated. A valid short/unknown state clears the previous readout; a malformed wire frame changes nothing. Readouts clear on connect/disconnect, do not use host telemetry and remain unchanged by `01:03` bud polls. The UI says *read-only, last full state* and does not expose an editor or write. D1301 also displays the captured post-sleep choice read-only (enabled byte 148 and action 144); this is not a timer, alarm, mixer, or request to play local audio. The timer (`15:03`) and alarm (`14:01`) need separate query integration, so they are NOT displayed. The A3945 state byte 70 is a standalone BassUp boolean, not a bitmask or EQ preset; the upstream parser supplies no setter or firmware floor. Its six per-model button assignments, EQ preset and gaming flag are also read-only. Whether the official mobile UI exposes the same independent BassUp switch on every firmware remains unverified. The simulator has explicitly synthetic values. Test coverage: model/command/length/checksum/invalid enum/range/late session, UI visibility and renderer **and** helper denial for valid researched write frames.

**Still blocked:** none of the newly researched write candidates currently has a demonstrated SoundControl-compatible *validated status ACK plus independent post-write and reconnect proof* for its exact model. The upstream library commonly assumes a same-command response means success and updates local state, which is insufficient for this app's safety requirement. A safe write requires matching the observed pre-state, queueing write and fresh query, rejecting stale replies/session/identity changes, checking changed field **and preservation of all other fields**, and reconnect testing with actual hardware captures. Never relax renderer or helper allowlists merely because a reference builder exists. Existing SoundControl toggles remain governed by their prior gates; this follow-up adds no new outbound bytes.
